## 결정: M3 통과, 계획 5(M4)로 간다

**M3의 통과 기준을 채웠다. 그래서 다음 단계인 계획 5(M4: 글자 품질)로 넘어간다.**

설계 문서 §9의 M3 통과 기준은 두 줄이다. "실험 동등성 목표를 맞춘다"(§9는 §5.4라고 적었지만 목표는 §5.5 끝의 "첫 번째 객관적 목표"에 있다), 그리고 "PowerPoint 복구 0, 출력이 매번 같다, 검증기 오류 0"이다.

- **실험 동등성: 통과.** 실험에 쓴 3장 덱(비공개 `4bd933b68041`)을 우리 변환기로 바꾼 PPTX가 다섯 조건을 모두 채운다. 평균 V1 raw 0.1984%(한도 0.26%), 장마다 V1 residual3 0/0/0 px(한도 25 px), 통째 그림 0, 개체 수 글상자 85·자유형 9·사각형 22·선 35·그림 1(기준 39/9/21/35/1 이상), 그라데이션 도형 하나(M3-R24). 같은 덱으로 M1의 실험 변환기는 평균 0.261%였다. 이 덱은 S1~S6도 세 장 모두 통과한다.
- **PowerPoint 복구 0.** 기록된 두 전체 측정(19개 덱×변형, 461장)과 이번에 다시 기록한 측정 모두에서 렌더가 시간 초과로 끝난 덱(렌더 종료 코드 2, 복구 창이 뜨면 이렇게 된다)이 0개다. 일부러 이상한 값을 담은 가장자리 덱 둘도 복구 없이 열린다(이번 `pytest --run-powerpoint`).
- **출력이 매번 같다.** Node와 Chromium, Edge, Firefox, WebKit이 6개 경우에 PPTX와 리포트의 해시까지 같다(이번 e2e). 19개 덱을 명령어 도구로 두 번 바꾼 PPTX가 측정에 쓴 것과 바이트까지 같다(이번에 다시 확인, 19/19). 수정 회차 뒤의 명령어 도구로 바꿔도 19/19가 같다.
- **검증기 오류 0.** Open XML 검증기(DocumentFormat.OpenXml 3.5.1, Office 2021 기준)가 측정의 출력 19개 모두에서 오류 0이다(이번에 다시 확인). 시험이 만드는 PPTX도 모두 오류 0이어야 시험이 통과한다. 수정 회차의 검증기(파일을 읽기 전용으로 열고, .NET이 읽지 못하는 링크 대상을 오류로 센다: M3-R61)로도 19개 모두 0이다.

- **V2의 한도는 작성자가 정했다(M3-R51, "원본만큼 허용").** 두 번째 측정에서 우리 V2 통과는 403/461장이다.

계획의 1단계 목록 밖에서, 관문의 증거를 이번 코드로 다시 확인했다. 모두 PowerPoint를 쓰지 않는다.

- **동등성 다시 판정.** 측정의 PPTX로 `parity.py`를 다시 돌렸다(전 기록에서 한 번, 다시 기록한 측정에서 한 번). 비공개 실험 덱은 두 번 모두 통과(종료 코드 0), 숫자는 위와 같다. `probe_std`는 두 번 모두 실패(종료 코드 1, 평균 0.2921%, 3쪽 residual3 108)로 기록과 같다.
- **두 번 변환.** 측정의 19개 덱(공개 4, 기능 지도 10, 비공개 5)을 지금의 명령어 도구로 두 번씩 바꿨다. 38개 PPTX가 모두 측정의 `out.pptx`와 바이트까지 같다. 다시 기록한 측정도 같은 명령어 도구 묶음(바이트까지 같다)으로 같은 PPTX를 냈다.
- **검증기.** 그 19개 PPTX를 검증기로 다시 봤다(다시 기록한 측정의 것도). 공개 14개는 전체 출력으로 오류 0, 비공개 5개는 `--private`(개수와 오류 id만)로 오류 0이다.
- **어림 개수.** 기능 지도 std PDF 7개를 바꿔 리포트의 어림을 셌다(아래 "작성기").

[--private]`가 파일마다 JSON 한 줄을 낸다. `--private`이면 파일 이름과 설명 없이 오류 개수와 id만 낸다(설명이 비공개 덱의 값을 인용할 수 있다). 종료 코드는 0(모두 오류 0), 1(오류 있음), 3(검증기를 돌릴 수 없음)이다. CI는 검증기를 빌드해 하네스 시험 단계 안에서 돌린다(M3-R4).

- 측정의 출력 19개: 오류 0(작업 12, 13, 이번).
- 시험: `writer.local`, `edge.local`(가장자리 덱), `convert.local`(probe_std, atlas-smoke_std 38쪽, 쪽 크기 덱 3개)이 만드는 모든 PPTX가 오류 0이어야 통과한다. 작업 12의 REDUCE_STOPS 실험 출력 8개도 오류 0이었다.
- 검증기의 범위가 ECMA-376보다 좁은 곳은 검증기를 따랐다(M3-R8).

### 작성기: 장면 요소가 무엇이 되나

`convert(bytes, { pages?, strict?, scene? })`(`packages/core/src/convert.ts`)는 쪽을 하나씩 읽어(`scenePages`), 정리 단계(`runPasses`)와 낮추기(`lowerSlide`)를 거쳐 `PptxWriter`(`packages/ooxml`)에 슬라이드를 하나씩 써 넣는다. 쓴 슬라이드는 리포트(`SlideReport`)만 남기고 놓는다. 그림 바이트는 처음 쓰는 슬라이드 앞에 한 번 쓰고 놓는다. `packages/ooxml`은 `fflate` 0.8.3에만 의존하고 `node:` 모듈을 쓰지 않아 모듈 워커에서 돈다. 명령어 도구 `deckback <in.pdf> -o <out.pptx> [--report <file.json>]`(`packages/cli`)와 웹 워커가 같은 `convert()`를 부른다.

**정리 단계**(순서대로, 입력 장면은 바꾸지 않는다):

1. 쪽 분류: `vector`, `image-only`, `print-frame`. 리포트에만 적는다(M3-R23).
2. 중복 제거: PDF/A의 같은 자리 중복 paint를 하나로(불투명한 것만).
3. 보이지 않는 것: 쪽에 아무것도 칠하지 않는 요소를 뺀다(알파 0 등).
4. 그라데이션 대체: 함수형 그라데이션과 메시, 글자 클립 안의 `sh`는 대체 요소와 메모가 된다(M3-R27).
5. 합치기: 같은 경로의 채우기와 선을 도형 하나로.
6. 클립: 쪽에서 아무것도 자르지 않는 클립은 버리고, 정확하면 기하에 접고(`sh`는 클립의 경로를 받는다), 아니면 `clip-dropped`나 `clip-approx`로 적는다(M3-R28).
7. 다시 합치기(M3-R29).
8. 그림: 그림의 클립을 그림 자신의 틀에서 판정해 버리거나, 자르기(`srcRect`)로 하거나, 클립 모양을 그림으로 채운 도형으로 한다. 그림 한 장의 타일 패턴은 그림 타일, 다른 타일 패턴은 `tile-unsupported`(M3-R31).
9. 채우기 규칙: nonzero 채우기의 `a:path`를 나눈다(M0-5). 증명하지 못한 곳은 `nonzero-approx`(M3-R19).
10. 모양 분류: `rect`, `line`, `custom`.

### V2 결정(M3-R51)

0003과 0004가 계획 4로 넘긴 V2 재보정을 했다. 우리 PPTX의 렌더가 생겨, 같은 슬라이드에서 렌더러끼리의 차이(잡음 바닥: MuPDF 렌더와 원본 PPTX의 PowerPoint 렌더 사이의 V2, M1-R33, M1-R57)와 우리 차이를 나란히 놓을 수 있게 되었다.

**첫 측정의 숫자**(작업 12, `v2_calibration.py`, 기능 지도 318장의 잡음 바닥):

| px32_shift1(%) | 0.251 | 1.547 | 4.026 | 6.450 |

| 5,000 px / 2% | p95 | 437 | 413 |

설계 문서의 50 px / 0.6%로는 원본 덱을 MuPDF로 그린 것조차 435장 중 329장만 통과한다. 브리프의 규칙대로 p99에 맞추면 몇 장의 비트맵·외곽선 슬라이드가 한도를 정해 거의 아무것도 막지 못한다. 그래서 컨트롤러가 작성자에게 선택지를 보였다.

**작성자의 결정(2026-11-11, "원본만큼 허용")**: 정답(원본 PPTX의 렌더)이 있는 슬라이드는 우리 residual5가 그 슬라이드 잡음의 residual5 + 50 px 이하이고, 우리 px32_shift1이 잡음의 px32_shift1 + 0.6% 이하일 때 통과한다. 설계 문서의 숫자가 "원본 자체의 렌더러 차이 위에 허용하는 초과분"이 된다. 정답이 없는 슬라이드는 400 px, 1%(기능 지도 잡음의 p90)다. `metrics.py`와 `run.py`가 이것을 쓰고(작업 13), V2 기록마다 어느 한도로 판정했는지(`limits.basis`가 `noise` 또는 `absolute`) 남긴다. 잡음 기록 자신의 `pass`는 정답 없는 한도로 본다(자기 자신과 비교하면 언제나 통과하기 때문이다).

### 크기를 센 예산과 메모리(M2-R36, M2-R37 → M3-R38~R41, M3-R59, M3-R60)

**무게(M3-R60, 최종 리뷰 F2).** 무게 1 단위가, 한 장을 변환하는 동안(장면을 만들고, 정리하고, 낮추고, XML로 쓰는 동안) 살아 있는 힙 약 100 B가 되게 요소 종류마다 재어 정했다. 잰 방법과 표는 `scene/weight.ts`의 주석에 있다. 종류마다 두 크기의 한 쪽 PDF를 `convert()`로 바꾸며, 장면을 만든 뒤(그 전의 pdf.js 쪽을 뺀다), 쓰기 직전, XML을 인코딩할 때 강제 GC 뒤의 힙을 잰 차이다. 전에는 요소마다 1이었다. 그 1은 경로 선분에는 약 100 B였지만 그림에는 1.7 KB였다. 그래서 그림 100,000개가 예산의 5분의 1인데 175 MB를 쥐었다.

| 종류 | 잰 바이트 | 단위 |
|---|---|---|
| 쪽의 그림 | 2,150 | 22 |
| 쪽의 도형 / 선분(`L`, `Z`) / 3차 곡선(`C`) | 2,627 / 401 / 849 | 26 / 4 / 8 |
| 하위 경로의 시작(`M`): 따로 쓰이는 한 선분짜리 하위 경로(M3-R49) 1,688 B 중 두 선분 802 B를 뺀 몫 | 886 | 4 + 9 = 13 |
| 쪽의 글줄 / 글자 | 4,525 / 102 | 45 / 1 |
| 링크 영역(pdf.js 자신의 주석 2,076 B는 뺐다) | 2,433 | 24 |
| 장면의 대체 요소(메모, 리포트의 메모 사본 포함) | 약 673 | 7 |
| 타일 칸·소프트 마스크 안의 요소(쓰이지 않는다) / 그 선분·글자 | 560 / 102 | 6 / 1 |

- 클립 경로는 선분마다 1이다. `sh`와 그림은 가장 큰 경로 클립의 선분을 자기 무게로도 센다. 정리 단계가 그 클립의 기하를 가져다 써서 쓰기 때문이다(5,000선분 클립 하나 안의 `sh` 200개가 전에는 무게 6,401에 120 MB였다).
- `SLIDE_WEIGHT_BUDGET = 500,000`(M3-R38, M3-R60). 약 50 MB이고, 새 단위로 가장 무거운 실제 슬라이드(`atlas_msprint.pdf` 37쪽, 157,538)의 3.2배다.
- `DECK_WEIGHT_BUDGET = 20,000,000`. 가장 무거운 덱(`atlas_msprint.pdf`, 1,243,470)의 16배다.
- 슬라이드가 대체 요소 하나 몫(7)을 남기지 못하게 되면, 그 범위(슬라이드, 타일 칸, 마스크)의 나머지는 `too-complex` 대체 요소 **하나**(메모 `slide too complex`, `coveredOps`는 처음 1,000개)가 된다(M3-R40). 그 자리에 닿은 글줄은 이미 가진 글자를 지키고 나머지가 그 대체 요소에 들어간다. 링크 영역도 무게를 갖고, 예산을 넘으면 버리고 센다(`droppedLinks.budget`).
- 덱 예산은 `convert()`만 켠다. 넘으면 뒤의 쪽은 읽지 않고 빈 `deck-too-complex` 슬라이드가 된다. `extractScene`은 M2 그대로다(M3-R41).

## 부록 A. Review Focus(M3)

M3 계획이 리뷰에서 특히 보라고 한 다섯 가지다. M3 코드의 "Review Focus N"이 이 번호를 가리킨다.

1. **PowerPoint가 "복구"할 수 있는 이상하지만 올바른 장면 입력.** 빈 기하나 한 점 기하, 높이 0인 가로선, 모두 0인 점선, 알파 0, 정지점이 하나거나 위치가 겹친 그라데이션, 빈 run, 제어 문자나 외톨이 서로게이트가 든 run, 빈칸이나 ASCII가 아닌 글자가 든 URL. 기대: 검증기 오류 0, PowerPoint가 복구 없이 연다. 시험: 작업 3(`edge-shapes`)과 작업 4(`edge-text`)를 CI에서 검증하고, `test_edge_decks_open_without_repair`(`powerpoint`)가 PowerPoint로 연다.
2. **PowerPoint가 받는 것보다 크거나 작은 쪽, 크기가 다른 쪽들.** 한 변이 4032 pt보다 크거나 72 pt보다 작은 쪽. 기대: 범위 안의 슬라이드 크기 하나, 모든 쪽을 고르게 늘이거나 줄여 가운데 놓고 배율을 리포트에 적는다. 시험: 작업 9, `convert scales an oversized page into PowerPoint's range`, `mixed page sizes are scaled to the first and centred`.
3. **하위 경로가 겹치거나 같은 방향으로 안에 든 nonzero 채우기 경로.** PowerPoint는 `a:path` 하나를 짝홀로 칠한다(M0-5). 기대: PDF와 같은 칠한 영역. 증명하지 못하면 리포트에 `nonzero-approx`. 시험: 작업 5, `fill rule: M0-5 cases A–D and crossing subpaths`.
4. **같은 PDF를 Node와 브라우저 워커에서.** 기대: 같은 `.pptx` 바이트와 리포트. 다르면 명령어 도구와 웹사이트가 다른 것을 낸다. 시험: 작업 9, `apps/web/e2e/convert-worker.spec.ts`.
5. **크거나 악의적인 덱.** 51쪽 덱, 선분 5,000개 칸을 200번 채운 M2의 1.2 KB PDF, M2의 깊이 7 중첩 패턴, 400쪽 덱. 기대: 크기를 센 예산으로 메모리가 묶이고, 슬라이드를 하나씩 zip에 쓰며, 넘친 것은 리포트에 적고 멈추지 않는다. 시험: 작업 9, `weight budgets bound the hostile PDFs`, `m0-perf.spec.ts`의 변환 단계(51쪽에서 100 MB 이하).
