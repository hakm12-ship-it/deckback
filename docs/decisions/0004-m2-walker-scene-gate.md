## 결정: M2 통과, 계획 4(M3)로 간다

**M2의 통과 기준을 채웠다. 그래서 다음 단계인 계획 4(M3: PPTX 작성기와 실험 동등성)로 넘어간다.**

설계 문서 §9의 M2 통과 기준은 "A단 PDF 100%에서 오라클과 일치한다"이다. A단은 우리가 PowerPoint로 직접 만들고 여러 방식으로 내보낸 시험 덱이다(설계 문서 §5.4). 이 기준을 M2에서 넓힌 계약(0002 §14~§19)으로 적용했다.

- A단 세트 두 개가 관문이다. `atlas`(OFL 글꼴 기능 지도의 6개 변형, COM으로 만든 보충 덱, 쪽 크기 덱 4개, probe. PDF 18개, 1,004쪽)와 `atlas-win`(Windows 글꼴로 만든 기능 지도, std와 notags. PDF 2개, 320쪽)이다.
- 1,324쪽 **모두** walker가 읽은 그대로(`ok`)도, 장면(Scene)이 돌려준 인벤토리로도(`sceneOk`) 오라클과 일치한다. 거절한 명령, 차이, 어림(`approx`) paint, 대체 요소, 메모, 실패한 슬라이드가 모두 0이다. 기록은 `fidelity/results/2026-11-10-oracle-sweep.json`이고, 최종 수정 묶음 뒤(`f7ed870`)에 다시 돌린 결과 파일도 이 기록과 바이트까지 같다(아래 "이번에 새로 돌린 결과").
- CI는 초록이다. 최종 수정 묶음의 마지막 코드 커밋 `f7ed870`의 실행 42768152808이 4분 56초에 성공했다.
- 최종 리뷰(브랜치 전체)가 찾은 Important 2건(중첩 타일 패턴의 요소 수, 글꼴 표의 Type 3 혼동)과 작은 항목들은 최종 수정 묶음이 고쳤고, 나머지는 판정으로 받아들이거나 다음 단계로 넘겼다(아래 "최종 리뷰와 최종 수정 묶음").
- 관문이 아닌 `producers`(다른 제작 도구, Skia PDF 6쪽)는 보고만 한다. 남은 차이는 모두 이유가 있다(아래 "넓힌 증거").
- 남은 작성자 일(npm 이름 예약, 받은 PDF 집계, 저장소를 공개하기 전에 정할 일)은 관문 판정과 무관하다.

Playwright의 Chromium 내려받기 한 단계가 8분 26초였다(그 전에는 약 18초). 러너의 일시적인 느림으로 보고 M2에서는 캐시를 바꾸지 않는다. 다시 그러면 Playwright 브라우저를 캐시한다(M2-R32). 전수 조사는 계획의 1단계 목록에 없지만, 관문의 증거라서 최종 커밋에서 한 번 더 돌렸다(PowerPoint를 쓰지 않는다). `npm run fidelity`는 다시 돌리지 않았다. M2는 측정 장치와 실험 변환기를 바꾸지 않았고, 0003의 기준 측정이 그대로 출발점이다.

### 통과 기준: 오라클 전수 조사(설계 문서 §9 M2)

`npm run oracle:sweep`(로컬, 요청할 때만 돈다)이 세 세트의 모든 쪽을 PyMuPDF 오라클과 0.05pt 허용 오차로 비교한다. 쪽마다 두 번 비교한다. walker가 읽은 인벤토리(`ok`)와, `extractScene`이 만든 장면에서 `inventoryOfSlide`가 다시 만든 인벤토리(`scene.ok`, 0002 §19)다. 기록은 작업 13이 남겼고(`DECKBACK_SWEEP_RECORD=1`), 수정 회차 뒤 `67fca2d`에서 다시 기록한 파일이 바이트까지 같았다.

| 세트 | 관문 | PDF | 쪽 | walker 일치 | 장면 일치 | 거절 | 차이 | 어림 paint | 대체 | 메모 | 실패 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| `atlas` | 예 | 18 | 1,004 | 1,004 | 1,004 | 0 | 0 | 0 | 0 | 0 | 0 |
| `atlas-win` | 예 | 2 | 320 | 320 | 320 | 0 | 0 | 0 | 0 | 0 | 0 |

- `atlas` 18개: 기능 지도(std, min, notags, pdfa, msprint 159쪽씩, hidden 161쪽), COM으로 만든 보충 덱 `atlas-com`(std, notags 5쪽씩), 쪽 크기 덱 4개(std, notags 4쪽씩), probe(std, notags 3쪽씩)다. `atlas-win`은 같은 기능 지도를 Windows 글꼴로 만든 것이다(160쪽씩, 이모지 슬라이드 하나가 더 있다).
- 전수 조사의 관문(`gateProblems`)은 관문 세트마다 `bySet`만 읽는다. 세트가 없거나, 있어야 할 PDF 20개 중 하나라도 빠지거나(M2-R30의 목록), 어느 쪽이든 walker 일치, 장면 일치, 거절 0, 실패 0, 대체 0, 메모 0(M2-R17), 어림 paint 0(M2-R33) 가운데 하나라도 어기면 실패한다(M2-R31). 합계는 producers를 더하므로 판정에 쓰지 않는다.
- **마스크가 걸린 관문 쪽**(M2-R15, M2-R28): `atlas_std.pdf` 39쪽(`atlas/fills/06`, 투명도 정지점이 있는 그라데이션)이다. 그라데이션 도형 4개가 각각 휘도(luminosity) 소프트 마스크 아래에 있고, 두 세트 모두에서 두 방식으로 일치한다. A단에서 소프트 마스크가 걸린 것은 변형마다 이 쪽의 4개뿐이다(pdfa와 msprint 변형은 이 쪽을 평평하게 내보내 마스크가 없다).
- **CI의 래칫**(`npm run test:corpus`): 커밋된 공개 자료 82쪽을 같은 두 방식으로 비교한다. 장면 쪽은 그 위에 슬라이드마다 스키마 검사, 대체·메모·실패 0, 정규 JSON의 SHA-256과 종류별 요소 수가 골든과 같은지, 덱의 글꼴 표와 출처의 해시(M2-R27)를 본다. 알려진 실패 목록 `fidelity/known/oracle-known.json`은 여전히 `{}`이다.
- **얼마나 비교했나**(작업 3~6의 측정, 오라클이 낸 값): `atlas` 세트는 채우기 14,470개와 선 6,646개(경로 선분 279,087개, 곡선 76,324개, 점선 162개), 글자 170,983개(글꼴 44개, 크기 77가지)이고, `atlas-win`은 채우기 2,852개, 선 2,142개(선분 76,584개), 글자 55,686개(글꼴 10개)다. `atlas_std.pdf` 한 파일에 그림 312개(회전 12, 뒤집힘 6), 축 그라데이션 102개, 원형 12개가 있고, 33쪽의 paint 307개는 쪽보다 좁은 클립 아래에 있다. 작업마다 한 필드를 일부러 틀리게 한 변형 코드로 돌려 그 필드의 차이가 정확히 나오는 것을 확인했다.

**이제 비교하는 것**(0002 §12, 비교 규칙과 허용 오차는 Global Constraints 그대로이고 하나도 넓히지 않았다):

**아직 비교하지 않는 것과 그 이유**:

- **타일 칸과 소프트 마스크의 내용.** 0002 §9대로 이것은 쪽의 내용이 아니라 패턴·마스크 데이터다. 오라클은 `begin_tile`..`end_tile`과 `begin_mask`..`end_mask`를 숨기고, MuPDF가 칸을 쪽에 바로 그리는 경우는 장치에서 쪽의 내용과 구별할 수 없어 칸을 표지 하나로 바꿔 둔다. 그래서 오라클이 칸과 마스크 안의 요소를 따로 내지 못한다. 장면은 이것을 `TileCell`과 `MaskDef`로 담고, 단위 시험, 그라데이션 픽셀 검사, 작업 8의 기능 지도 검사(`atlas_std.pdf` 타일 칸 85개, 마스크 4개)가 본다. 오라클과의 값 비교는 아니다.
- **정확한 글자 클립 상자.** walker의 글자 클립 상자는 어림값이고(§5), 그 아래의 paint에는 `approx`·`clipApprox`가 붙어 꼴만 비교한다. 정확한 상자에는 글꼴 프로그램의 글리프 경계가 필요하다. A단 1,324쪽에 어림 paint가 0개라서 만들지 않기로 했다(0002 §13 첫 줄). 전수 조사 관문은 관문 세트의 어림 paint가 0개일 것을 요구하므로(`gateProblems`, M2-R33), 이런 paint가 A단에 생기면 관문이 실패해 바로 드러난다.
- **축·원형 그라데이션의 좌표와 색 멈춤.** MuPDF의 파이썬 연결이 `fz_shade`의 좌표를 주지 않는다(§13). 대신 `gradient.local.test.ts`가 장면의 그라데이션으로 계산한 색을 MuPDF 렌더의 픽셀과 비교한다. 6개 경우의 최악 차이가 3.94이고 허용치는 ±8이다(작업 8).
- **그라데이션·패턴으로 칠한 글자의 `shade`·`pattern`을 장면 쪽에서**(M2-R26, §19). 장면은 그 패턴을 `TextRun.fill`에 두지만, walker가 이 paint를 내는 단위(글자 묶음)의 끝이 장면에 남지 않는다. A단에는 0개이고 Skia 표본 두 쪽에만 있다.

### 장면 스키마 v1

`extractScene(bytes, { pages?, strict? })`(`packages/core/src/scene/extract.ts`)가 PDF를 장면으로 바꾼다. 쪽을 하나씩 읽고, walk하고, 만들고, 놓는다. 기본은 멈추지 않는 방식(lenient)이다. 읽지 못한 쪽은 `failed: 'page-unreadable'`, 만들지 못한 슬라이드는 `slide-unbuildable`이고, 덱은 계속된다. 모형이 없는 명령은 대체 요소(`FallbackEl`)와 메모(`Note`)가 된다.

**스키마가 고정하는 것**(`scene.schema.json`, draft-07, `$id` `deckback.scene/1`):

- 덱(`SceneDeck`: `source`, `fonts`, `media`, `slides`)과 슬라이드(`sizePt`, `elements`, `clips`, `masks`, `notes`, `failed`). 요소는 도형(`shape`), 글줄(`textline`), 그림(`picture`), 대체 요소(`fallback`), 링크 영역(`hotspot`) 다섯 가지다.
- 모든 구조가 `additionalProperties: false`이고 모든 필드가 필수다. 블렌드 모드는 16가지 이름, `media`의 키는 SHA-256 16진수다. ajv(strict)가 경고 없이 읽는다.
- id: 요소 `p<쪽>:z<명령 번호>`(같은 명령의 다음 요소는 `:1`, `:2`), 타일 칸 안 `<주인 id>/z<n>`, 링크 영역 `p<쪽>:a<n>`, 글꼴 `f1`, `f2`…(처음 쓴 순서), 클립 `c<n>`, 마스크 `m<n>`. 쪽 번호는 1부터다(M1-R50, M2-R22).
- 반올림(M2-R13, M2-R20): 슬라이드 좌표의 길이는 소수 셋째 자리, 단위 없는 값과 칸·그라데이션 공간의 수는 여섯째 자리, -0은 0. 정규 JSON은 키를 정렬하고, 시각과 pdf.js 문서 id를 담지 않는다. 해시는 `globalThis.crypto.subtle`의 SHA-256이다.
- 그림: 평범한 JPEG은 원본 바이트 그대로, 나머지는 결정적인 PNG(fflate 0.8.3 고정, 압축 수준 6)다. 같은 바이트는 한 번만 담는다.
- `packages/core/src`에는 `node:` import도 ajv도 없다. 시험이 확인한다.

- 첫 로딩은 M0의 512,677 B에서 장면 코드 때문에 늘었다(작업 11 전 516,551 B). 최종 수정 묶음의 코드(요소 예산, 칸 경로)가 410 B를 더했다. 쪽당 시간은 처음 엔진을 읽는 시간까지 넣은 평균이다.

- Node에서는 `atlas_std.pdf` 159쪽이 3.0초(쪽당 19 ms), 장면 JSON이 약 7.1 MB다(작업 11).
- **작은 PDF가 메모리를 다 쓰는 경우**(최종 리뷰 F1, M2-R36): 타일 패턴의 칸에서 다른 타일 패턴을 채우고 그것을 다시 겹치면, 칸을 채우는 요소마다 칸이 통째로 복사되어 요소 수가 깊이마다 10배가 된다. 칸마다 10개, 깊이 5인 3.3 KB PDF가 요소 111,111개, 장면 JSON 39.1 MB였고(extractScene 751 ms, walker만 211 ms), 깊이 7은 walker에서 2 GB 힙을 넘겨 멈췄다. 이제 walker는 다른 칸마다 쪽당 한 번만 걷고, 슬라이드는 요소를 100,000개까지만 만든다. 그 뒤의 타일 칸은 만들지 않고, 칸을 채우던 요소가 같은 id의 대체 요소(`too-complex`)와 메모 `tile cell too large`가 된다. 엄격한 방식은 `SceneTooComplexError`를 던진다. 예산은 관문 세트와 51쪽 덱에서 가장 바쁜 슬라이드(`atlas_msprint.pdf` 37쪽, 중첩 포함 요소 2,773개)의 10배 이상이고 100,000 이상인 가장 작은 둥근 수다. 깊이 5는 이제 요소 100,001개, 35.2 MB, 230 ms이고, 깊이 7(4.5 KB)은 100,021개, 35.8 MB, 231 ms다(walker는 둘 다 몇 ms). **이 예산은 요소의 개수만 센다. 요소 하나의 크기(경로 선분, 글자)는 세지 않으므로 슬라이드 하나의 메모리도 아직 묶이지 않는다.** 묶음을 다시 리뷰하며 1.2 KB PDF로 보였다. 선분 5,000개짜리 칸 하나를 200번 채우면 요소는 400개뿐이지만 경로 선분이 1,001,400개, 장면 JSON이 10.1 MB다. 칸이 그것을 채우는 요소마다 복사되는 것(작업 8)이 그대로이기 때문이다. 크기를 센 예산(경로 선분과 글자)은 덱 전체의 예산과 함께, 슬라이드를 하나씩 써 나가는 PPTX 작성기가 생기는 M3에서 다시 설계한다(M2-R36, M2-R37). 그때까지 몇 KB짜리 악의적인 PDF가 슬라이드 하나에 수백 MB를 쓸 수 있고, 쪽이 많으면 쪽마다 그만큼 더 쓸 수 있다. 실제 덱은 근처에도 가지 않는다(관문 세트에서 가장 바쁜 슬라이드가 요소 2,773개다).

**검사로 고정한 다섯 가지**(부록 A의 Review Focus): 모르는 명령은 메모와 대체 요소가 되고 뒤의 칠하기는 남는다. 소유자 암호만 있는 PDF는 `source.encrypted`가 참이고 JPEG을 PNG로 다시 만들며 글꼴 이름은 pdf.js의 것으로 돌아간다. 망가진 글꼴 프로그램은 그 글꼴의 이름만 잃고, 읽지 못한 쪽은 그 슬라이드만 `failed`가 된다(실패한 쪽이 다른 쪽의 글꼴·미디어 키를 바꾸지 않고, 그 쪽의 태그도 `source.tagged`에 남지 않는다). Node와 브라우저가 같다. 큰 덱의 메모리는 위와 같다. 중첩 타일 패턴으로 요소가 수백만 개가 되는 작은 PDF도 슬라이드마다 요소의 개수는 예산으로 묶인다(`extract.test.ts`의 깊이 5와 깊이 7 시험). 요소의 크기는 아직 묶이지 않는다(위, M2-R37).

## 계획 4(M3)에 넘길 사실

- **V2 재보정은 계획 4로 옮겼다(0003 바로잡기).** 0003의 "계획 3에 넘길 사실"은 "계획 3은 V2를 기능 지도 전체의 근거로 다시 보정해야 한다"고 적었다. 계획 3은 이것을 하지 않았고, 계획 4(M3)로 옮겼다. 다시 보정하려면 **우리가 만든 PPTX의 렌더**가 있어야 하기 때문이다. M1의 기록으로는 변환기 없이 렌더러 차이만으로도 기능 지도 159장 가운데 42장(atlas-smoke 38장 가운데 11장)이 V2를 넘는다. 실험 변환기의 출력으로는 이 잡음과 변환기의 잘못을 가를 수 없다. 계획 4의 PPTX 작성기가 첫 출력을 낼 때 그 렌더와 잡음 바닥(M1-R33, M1-R57)을 함께 놓고 V2를 정한다. 그때까지 V2 기준값은 그대로다. `fidelity/README.md`의 같은 문장도 작업 14의 문서 커밋(`3403b33`)에서 고쳤다.
- **정리 단계(pass)의 첫 입력: 장면이 이미 담고 있는 증거.**
  - 채우기 규칙: 도형의 `fillRule`. M0-5대로 nonzero 경로의 겹친 하위 경로는 `a:path`를 나누거나 도형 연산이 필요하다.
  - 선: `LineStyle.anisotropic`(M2-R4). 축마다 배율이 다른 CTM에서 `a:ln`의 두께 하나는 평균일 뿐이다.
  - 그림: `xfrm`(회전, `flipH`/`flipV`), `skewed`, 원래 행렬, 연산자의 픽셀 크기 `px`(M2-R16). JPEG은 그대로, 나머지는 PNG다.
  - 그라데이션: 선형·원형의 정지점, `extend`, 그라데이션 공간의 행렬. 함수형과 메시는 `{ kind: 'shading' }`뿐이라 그림 대체가 필요하다. M0-6대로 표본 정지점을 유지한다.
  - 타일: 칸 공간의 `TileCell`(여섯째 자리, M2-R20). JPEG 칸은 그대로 넘어온다(M2-R18).
  - 클립, 그룹, 블렌드, 마스크: 클립 사슬(`path`, `box`, 어림 `text`), `GroupRef`(알파, 블렌드, isolated, knockout, 상자, 가져간 마스크), `MaskDef`(휘도·알파, 배경색).
  - 글자: `TextRun`의 원래 증거(자간 Tc, 장평 Tz, 기준선 이동, 기울기, `fillMode`, 기준선 위치와 각도, 세로쓰기). 가짜 굵게(Tr 2, Windows 글꼴판 6쪽 45덩어리)와 가짜 기울임은 M4가 이 증거로 판단한다. `FontInfo`(영어·한국어 이름, 굵게·기울임, 수치, `fsType`)는 S6의 글꼴 이름 검사(M1-R71)의 입력이다.
  - 출처: `provenance`(명령 번호, MCID, 구조 경로). 요소 id `p<쪽>:z<명령>`은 S4가 읽는 출처 이름 `pdf:p{쪽}:z{순서}`(M1-R50)와 같은 꼴이다.
  - 대체 요소: `unsupported-op`, `unbuildable`, `image-unreadable`, `stencil-pattern`, `shading-unreadable`. 모두 `raster: null`이고, 그림 대체 렌더러(M5)가 채운다.
  - 링크 영역: 안전한 URL(http, https, ftp, mailto, tel)만, `link.dest`는 `page:<n>`(1부터).
- **장면이 아직 담지 않는 것**(작업 8~11에서 미룸): 소프트 마스크의 `/TR`, 그라데이션의 `/Background`와 자기 `/BBox`, 소프트 마스크 `/G` 안의 JPEG(PNG가 된다), 패턴으로 그린 글자의 선 패턴(`TextRun.stroke`가 `null`이고 메모가 남는다). 클립이나 마스크에 유한하지 않은 수가 있으면 그 슬라이드 전체가 메모 없이 `slide-unbuildable`이 된다(최종 리뷰 F11). 글줄을 만들지 못한 글자 덩어리는 첫 글자 크기의 대체 요소 하나가 되고 뒤의 글자는 빠진다(F6). 모두 M5에서 본다(M2-R35).
- **최종 리뷰에서 넘어온 것**(M2-R34~R36):
  - 메시(와 함수형 그라데이션): 계획의 Review Focus 1은 메시를 대체 요소와 메모로 보지만, 작업 7의 `Fill` 형은 `{ kind: 'shading' }`으로 두고 "뒤 단계가 대체 요소를 만든다"고 한다. 코드는 형을 따른다(종류는 남아 잃는 것은 없다). 계획 4가 "`shading` 채우기는 그림 대체 요소와 메모가 된다"를 분명히 담아야 한다(F9).
  - JPEG을 그대로 넘길 때 표본 정밀도와 프레임 종류를 보지 않는다. 8비트이고 SOF0이나 SOF2일 때만 그대로 넘기도록 M3에서 고치고, PowerPoint가 우리 출력을 그릴 때 확인한다(F10).
  - `ExtractOptions.pages`에 같은 쪽이 두 번 있으면 슬라이드 번호와 요소 id가 겹친다. M3의 명령어 도구에 쪽 선택이 생길 때 거절할지 정한다(F12).
  - 덱 전체의 예산과, 요소의 개수가 아니라 크기(경로 선분과 글자)를 센 예산은 M3(위 "큰 덱", M2-R36, M2-R37).
  - `Math.atan2`가 결정적 출력의 길에 남아 있다(그림과 글줄의 각도). ECMAScript가 근사만 정하는 함수라 엔진마다 마지막 비트가 다를 수 있지만, 6자리 반올림의 경계에서만 출력이 바뀌고 e2e의 네 엔진이 모든 경우에 같은 해시를 냈다. 받아들인다(M2-R34). M3의 PPTX 해시가 엔진마다 달라지면 바꾼다.
- **글꼴(M4로 미룸)**: 타일 칸이나 소프트 마스크 안에서만 쓴 글꼴은 pdf.js의 이름으로 돌아간다(`fontPrograms`가 그 자원을 걷지 않는다). CP949 이름과 Latin-1 글자뿐인 UTF-8 이름은 바이트마다 한 글자다. 한국어 이름표만 굵게라고 하는 OFL 글꼴이 있다(영어 이름표가 정한다). 임베드하지 않은 글꼴의 `latinName`에 MT/PS 꼬리가 남는다.
- **0003에서 그대로 넘어가는 것**: S4는 출처 이름을 쓰지 않는 변환기에서 n/a다. S3의 프리셋 기하(presetShapeDefinitions)를 넣을지(M1-R47), S2의 순서 민감성(M1-R63)은 실제 변환기의 데이터로 다시 본다. 0003의 "기준 측정" 표가 여전히 출발점이다.

## 최종 리뷰와 최종 수정 묶음

작업 14 뒤에 브랜치 전체(`c5fffce..3403b33`)를 다시 리뷰했다. 결론은 "고친 뒤 병합"이었다. Critical은 없고, Important 2건과 Minor 10건이 나왔다. 최종 수정 묶음(`3403b33..f7ed870`의 커밋 8개와 이 문서의 커밋)이 다음을 고쳤다. 장면 골든과 덱 키는 바이트까지 그대로이고, 전수 조사 결과 파일도 커밋된 기록과 바이트까지 같다. 관문 세트, producers, 커밋된 자료와 51쪽 덱의 PDF 31개의 장면 해시도 묶음 전과 같다.

- **중첩 타일 패턴(Important F1, M2-R36)**: 위 "큰 덱"의 마지막 항목. walker는 다른 칸마다 쪽당 한 번 걷고(같은 패턴의 칸들이 걸은 결과를 함께 쓰며, 소프트 마스크는 거쳐 온 칸의 경로로 알아봐 출력이 바뀌지 않는다), 슬라이드는 요소 100,000개 예산을 넘으면 칸을 만들지 않고 `too-complex` 대체 요소와 메모 `tile cell too large`를 남긴다. 예산은 요소의 개수만 세므로 슬라이드 하나의 메모리는 아직 묶이지 않는다(M2-R37). 관대한 방식이 칸의 요소를 단계마다 다시 검사하던 것도 한 번만 하게 했다.
- **글꼴 표의 Type 3 혼동(Important F2)**: 이름만으로 글꼴 프로그램을 찾아서, /BaseFont가 같은 Type 3 글꼴이 먼저 있으면 진짜 글꼴이 `type3: true`에 이름 없는 글꼴이 되었다. 이제 Type 3 여부가 pdf.js와 같은 프로그램만 짝짓고, 빈 이름은 짝짓지 않으며, `type3`은 pdf.js의 값만 쓴다. 장면의 인벤토리와 walker가 이제 우연이 아니라 만든 방식으로 같다.
- **Minor**: `source.tagged`는 만든 슬라이드의 쪽에서만 정한다(F3). 읽지 못한 링크 목록은 strict 방식에서도 메모다(F4, M2-R25). 타일 칸 안 메모의 `opIndex`와 `op`가 서로 다른 연산자를 가리킨다는 것을 문서에 적었다(F7). 이 문서의 판정 목록에 M2-R32~R36을 더하고 이 단락을 다시 썼다(F8).
- **전수 조사 관문(M2-R33)**: 관문 세트의 어림 paint 0개도 요구한다. 위 "아직 비교하지 않는 것"의 문장이 이제 사실이다.
- **미뤄 두었던 작은 항목**: 전수 조사의 `[...gate, ...refused]` 배선을 도우미(`recordBlockers`) 하나로 합쳐 단위 시험이 같은 배선을 시험한다. 커밋된 스키마 `/3` 전수 조사 기록 모두에 `recordProblems`를 돌리는 단위 시험을 더했다. `make_skia.mjs`는 호스트가 있는 `file:` URL(SMB로 네트워크를 탄다)을 거절하고, Skia 쪽의 정적 검사가 `@import`, `srcset`, `image-set()`도 본다. `com_deck`의 위치 검사 시험이 `run_author`도 막아, 위치 검사가 망가져도 보통 pytest 실행이 PowerPoint를 띄우지 않는다. harness README와 `com_deck.py` 설명(기능 검사는 `powerpoint` 시험이 한다, `AuthorError`에는 이유 필드가 없다), 0002 §13의 Type 3 폭 줄과 숨긴 폼 `/OC` 줄의 분류를 바로잡았다.
- **받아들인 것과 넘긴 것**: `Math.atan2`는 받아들였다(F5, M2-R34). 실패한 글자 덩어리의 대체 요소가 첫 글자만 덮는 것(F6)과 유한하지 않은 클립이 슬라이드를 메모 없이 비우는 것(F11)은 M5, 메시를 대체 요소로 만드는 일(F9)은 계획 4, JPEG을 그대로 넘길 때의 정밀도와 프레임 종류(F10)와 `pages`의 중복(F12)은 M3, 덱 전체의 예산과 크기를 센 예산은 M3로 넘겼다(M2-R35, M2-R36, M2-R37). 위 "계획 4(M3)에 넘길 사실"과 "장면이 아직 담지 않는 것"에 적었다. 리뷰의 나머지 미룬 항목은 리뷰의 분류대로 그대로 둔다.
- **다시 리뷰와 마무리 수정**: 묶음을 다시 리뷰해 여덟 항목이 모두 고쳐졌음을 확인했다. 칸을 함께 걷는 변경은 리뷰가 따로 만든 PDF(같은 패턴과 복사한 패턴, 다른 CTM과 폼, PaintType 2의 색, 쪽의 소프트 마스크, 마스크·글자·인라인 그림이 든 중첩 칸)에서도 관대한 방식과 엄격한 방식 모두 정규 JSON과 미디어가 같았다. 남은 것 가운데 예산이 요소의 크기를 세지 않는다는 것은 M3로 넘겼고(M2-R37, 위 "큰 덱"), 작은 것들은 마무리 수정이 고쳤다. 깊이 7 시험의 2초 단언은 약 10초의 멈춤 방지로 바꾸고 그 대신 칸마다 한 번 걷는지를 센다. `allowedRequest`는 호스트는 비었지만 경로가 UNC처럼 읽히는 `file:` URL(`//`로 시작하는 경로, 백슬래시, `%5C`, `%2F`)도 거절한다. 이 문서의 시간 숫자를 측정값(528 ms, 231 ms)으로 고쳤다.

## 안전 기록(PowerPoint와 저장소)

**요약.** M2 동안 작성자의 문서나 작성자가 띄운 PowerPoint는 한 번도 관련되지 않았다. PowerPoint 프로세스를 강제 종료(kill)한 적은 한 번도 없다. PowerPoint를 쓴 작업은 작업 1과 작업 14뿐이다(작업 13은 다시 내보낼 일이 없었다). 그 밖의 작업과 최종 수정 묶음은 PowerPoint를 쓰지 않았다. PowerPoint를 쓸 때마다, 그리고 쓰지 않은 작업 가운데 여섯 작업(5, 6, 8, 10, 11, 13)과 최종 수정 묶음에서 읽기 전용 `Get-Process POWERPNT` 확인을 했다. 확인한 모든 시점에 작성자의 PowerPoint는 실행 중이 아니었다. 보인 PowerPoint는 모두 그 실행이 띄운 것이었다(작업 1의 1개, 작업 14의 2개, 아래). 그래서 "작성자가 PowerPoint로 일하는 중"이라는 상황은 M1처럼 시험의 대역으로만 검증했다.

1. **작업 1(기능 지도 보강)**:
   - 창 없는 탐색 실행 하나가 COM 참조를 스크립트 변수에 남겼다. 그래서 그 실행이 띄운 창 없는 PowerPoint가 모듈의 `Quit()` 뒤에도 약 12분 살아 있다가 스스로 끝났다(DCOM 정리). 모듈은 "아직 실행 중, 종료하지 않음"이라고 보고했다. 에이전트는 모듈 밖에서 닫거나 끝내거나 죽이지 않았다(M1-R73). 그동안 작성자의 PowerPoint는 실행 중이 아니었다. 그 뒤의 실행은 모든 참조를 놓았고 아무것도 남기지 않았다.
   - SmartArt를 만들려고 창을 열지 않았다(M2-R7).
   - 리뷰 지적 두 가지를 고쳤다. 작성 스크립트의 슬라이드별 `catch`가 PowerPoint의 "바쁨" 거절을 슬라이드 실패로 삼켜 거짓 `excluded`를 쓸 수 있었다(M1-R74). 또 COM 속성 읽기는 거절을 `$null`로 바꿀 수 있어서, 모든 속성 읽기와 쓰기를 던지는 함수로 바꿨다. 이 시험에서 창 없는 실행을 13번 했다. 13번은 pytest 호출 세 번에 나뉘어 있었고(고치기 전 5번, 고친 뒤 7번, 이름 확인 1번), 읽기 전용 확인은 실행마다가 아니라 pytest 호출마다 그 전후에 했다. 세 호출 모두 전후 POWERPNT는 0개였다.
   - 세션이 끝나면서 재검토 에이전트가 결과 없이 멈춘 적이 있다(커밋 없음, 작업 트리 깨끗, PowerPoint 꺼짐). 작성자의 질문에 따라 이어서 했다.
2. **작업 2~13과 최종 수정 묶음**: PowerPoint를 쓰지 않았다. 임시 파일은 시스템 임시 폴더 아래 새 폴더에 두었다. 작업 4와 작업 5의 일회용 탐색 시험 파일이 잠깐 저장소의 시험 폴더 안에 있었고, 커밋 전에 지웠다. 최종 수정 묶음은 pytest를 `--run-powerpoint` 없이만 돌렸다. 하네스 전체 실행 두 번의 전후와 묶음을 끝낼 때 한 읽기 전용 확인에서 POWERPNT는 언제나 0개였다. 고친 위치 검사 시험이 위치 검사를 일부러 끈 변이에서 실패하는지도 확인했는데, 그 시험은 `run_author`를 막으므로 PowerPoint를 띄우지 않았다.
3. **개인정보**:
   - 작업 4부터 차이 줄에 글꼴 이름과 글자가 들어간다. 그래서 커밋되는 전수 조사 기록에는 공개 세트만 들어간다. 작업 13의 리뷰에서, 기록기가 `out/producers`에 무엇이 있든 믿는다는 점이 나왔다(비공개 PDF를 거기 두면 그 이름과 글자가 커밋될 수 있었다). 실제로 그런 기록이 커밋되기 전에 M2-R30으로 막았다. 이제 커밋된 출처에서 나오지 않은 이름이 하나라도 있으면 기록하지 않고, 거부 메시지에도 이름 없이 세트와 개수만 나온다. 다시 기록한 파일은 바이트까지 같았다. 커밋된 기록에는 경로, 사용자 이름, 비공개 이름이 없고, 이름은 공개 이름 24개뿐이다.
   - 장면 JSON은 어떤 덱의 것도 커밋하지 않는다. 골든은 해시와 개수뿐이다. 메모와 대체 요소의 글은 명령 이름과 고정 문구뿐이다. 장면을 만들다 던진 오류는 이름(`TypeError` 등)만 남기고 메시지는 남기지 않는다.
   - 위 "남은 항목"의 기록 검사: M2 커밋은 비공개 파일 이름도, 비공개 덱에만 있는 글꼴·도형 이름도 더하지 않았다.
4. **기본 프린터**: 0003은 M1의 msprint 내보내기가 기본 프린터를 바꿨는지 알 수 없다고 적었다. 2026-11-10 최종 실행 전에 읽기 전용으로 확인한 이 PC의 기본 프린터는 "Microsoft Print to PDF"이고, "Windows가 기본 프린터를 관리" 설정이 켜져 있다(`LegacyDefaultPrinterMode` 0). 최종 실행의 `pytest --run-powerpoint`에는 probe 덱을 여섯 변형 모두(msprint 포함) 임시 폴더로 내보내는 시험이 있고, 그 시험은 기본 프린터가 바뀌지 않았거나 되돌려졌음을 확인한다. PowerPoint 시험이 끝난 뒤 다시 읽은 기본 프린터도 "Microsoft Print to PDF"였다. 기본 프린터는 읽기만 했고 바꾸지 않았다. 기능 지도의 msprint PDF는 M1에서 내보낸 것을 그대로 썼다. 기본 프린터가 처음부터 이것이었는지는 여전히 알 수 없으니, 작성자는 원하는 프린터인지 확인하면 된다.
5. **작업 14(최종 실행, 2026-11-10)**:
   - 작성자에게 미리 알린 뒤, PowerPoint를 쓰는 세 시험을 PowerPoint를 쓰지 않는 시험 뒤에 이어서 돌렸다.
   - 첫 실행에서 읽기 전용 `Get-Process POWERPNT` 확인을 8번 했다(시작 전, 세 시험 각각의 전후, 끝난 뒤). 시작 전, `pytest --run-powerpoint` 전후, `test_com_module.ps1` 전에는 0개였고, `test_com_module.ps1` 뒤로는 끝까지 2개였다.
   - 원인: `test_com_module.ps1`의 (f) "시작 화면" 경우가 스스로 띄운 PowerPoint를 보이게 하자, Office의 개인 정보 안내 대화 상자가 떴다. 대화 상자가 열린 PowerPoint는 COM 호출을 거절한다. 시험은 자기 인스턴스를 끝내려고 시험용 덱을 보호된 보기로 열고 응용 프로그램을 놓은 뒤 그 창을 닫는데, 그 닫기(또는 열기)가 `RPC_E_SERVERCALL_RETRYLATER`로 거절당했다(시험의 기록으로는 둘 중 어느 쪽인지 가를 수 없다). 그래서 세션 확인 1개가 실패했고, 그 인스턴스가 보호된 보기 창과 함께 실행 중으로 남았다. 그 1초 뒤에 시작한 두 번째 POWERPNT 프로세스(보이는 창이 없다)도 남았다. 이것은 시작 시각으로 보아 보호된 보기의 샌드박스 프로세스로 짐작한 것이고, 확인하지는 않았다. 이어서 `test_render_safety.ps1`은 그 PowerPoint를 "이미 실행 중"으로 보고 붙으려다 `RPC_E_CALL_REJECTED`로 확인 1개가 실패했다. 대역 프레젠테이션을 더하기 전이다.
   - 이 대화 상자는 M1의 최종 실행(2026-11-05)에는 나오지 않았다. COM 모듈과 두 시험의 코드는 M2에서 바뀌지 않았다.
   - 남은 PowerPoint 두 프로세스는 이 실행이 띄운 것이다. 하나는 시험의 기록에 그 프로세스 번호가 "이 실행이 띄운 PowerPoint"로 남았고 창 제목이 시험용 덱의 보호된 보기다. 다른 하나는 그 1초 뒤 같은 시험 중에 시작했다(위의 짐작). 둘 다 `test_com_module.ps1` 전에는 없었으므로 작성자의 PowerPoint가 아니다. 에이전트는 대화 상자에 답하지 않았다(작성자가 정할 개인 정보 선택이다). 아무것도 닫거나 끝내거나 죽이지 않았다. 임시 복사본과 작업(job) 프로세스는 남지 않았다.
   - 에이전트는 여기서 멈추고 보고했다. 컨트롤러가 작성자에게 물었고, 작성자가 대화 상자에 직접 답했다. 작성자는 실행이 연 창만 닫아 달라고 했다.
   - **닫은 것.** 작성자가 답한 뒤에도 POWERPNT는 같은 두 프로세스였다. 대화 상자는 사라졌고, 보이는 창은 보호된 보기 창 하나뿐이었다.
     - 에이전트는 COM 모듈의 `Connect-DeckbackPowerPoint`(이미 실행 중인 것에 붙기)로 붙어서 열린 것을 읽었다. 프레젠테이션 0개, 문서 창 0개, 보호된 보기 창 1개였고, 그 창의 원본은 시험의 작업 폴더에 있는 시험용 덱이었다.
     - 그 창 하나만 닫았다. 순서는 시험의 `Close-OwnVisibleInstance`와 같다. 모듈의 `Disconnect-DeckbackPowerPoint`로 응용 프로그램을 먼저 놓은 다음 창을 닫았다.
     - 이 세션은 그 PowerPoint를 자기가 띄웠다고 증명할 수 없다. 그래서 모듈은 `Quit()`을 부르지 않았고, 에이전트도 부르지 않았다.
     - 마지막 창이 닫히자 그 인스턴스는 5초 안에 스스로 끝났다. 두 번째 프로세스도 같은 때 저절로 사라졌다(보호된 보기의 샌드박스라는 짐작과 맞는다). 그 뒤 POWERPNT는 0개였다.
   - **다시 실행.** POWERPNT 0개에서 두 시험을 이어서 다시 돌렸다. 두 시험 모두 전후 0개였고, 대화 상자는 다시 뜨지 않았다.
     - `test_com_module.ps1`은 `COM MODULE TESTS OK`(91초), `test_render_safety.ps1`은 `SAFETY OK`(31초)다.
     - 두 시험 모두 자기가 띄운 PowerPoint를 시험 자신의 방법으로 끝냈다.
     - 기본 프린터는 다시 실행한 뒤에도 "Microsoft Print to PDF"였다.
   - 읽기 전용 확인은 모두 20번이다. 첫 실행 9번(손으로 한 시작 전 확인 포함), 멈출 때 1번, 다시 시작할 때 1번, 창을 닫기 전후 2번, 다시 실행 6번, 끝난 뒤 1번이다. 작성자의 PowerPoint는 어느 시점에도 실행 중이 아니었다. 남은 PowerPoint, 임시 복사본, 작업(job) 프로세스는 없다.
   - **교훈.** 시험이 PowerPoint를 보이게 하면 Office가 처음 실행 안내를 띄울 수 있다. 대화 상자가 열린 PowerPoint는 COM 호출을 거절한다. 시험은 그 거절을 실패로 보고했고 아무것도 죽이지 않았다. 모듈의 안전 규칙은 그대로 지켜졌다.
   - PowerPoint를 쓰는 시험은 시험 자신이 띄운 PowerPoint와 고유한 이름의 임시 복사본, 저장하지 않은 대역 프레젠테이션만 썼다. 아무것도 강제 종료하지 않았다. `test_com_module.ps1`과 `test_render_safety.ps1`은 PowerPoint가 꺼져 있을 때 잠깐 PowerPoint 창을 띄운다.

## 부록 A. Review Focus(M2)

M2 계획이 리뷰에서 특히 보라고 한 다섯 가지다. M2 코드의 "Review Focus N"이 이 번호를 가리킨다.

1. **walker가 모형으로 만들 수 없는 것을 쓰는 쪽**(SVG에서 온 폼, 메시, 처음 보는 연산자). 기대: 변환이 계속되고 쪽의 나머지는 그대로이며, 쪽의 `notes`와 `fallback` 요소가 무엇을 건너뛰었는지 말한다. 아무것도 던지지 않는다. 시험: 작업 11, `lenient: an unknown operator becomes a note and a fallback and later paints survive`.
2. **소유자 암호만 있는 PDF**(`rawpdf`가 읽지 못한다). 기대: 도형과 글자는 pdf.js로 나오고, JPEG은 다시 인코딩하며, 글꼴 이름은 pdf.js의 것으로 돌아가고, `source.encrypted`가 참이다(설계 문서 §8). 시험: 작업 11, `an owner-password PDF gives a scene flagged encrypted`.
3. **망가진 객체 하나**(깨진 글꼴 프로그램, pdf.js가 목록을 만들 수 없는 쪽 하나). 기대: 그 글꼴만 이름을 잃거나 그 슬라이드만 `failed`이고, 다른 쪽은 바뀌지 않는다. 시험: 작업 9, `a damaged font program keeps the run and loses only the names`. 작업 11, `a page that cannot be listed becomes a failed slide and the deck continues`.
4. **같은 파일을 Node와 브라우저 워커에서.** 기대: 정규 장면 JSON과 미디어 해시가 같다. 다르면 나중에 명령어 도구와 웹사이트가 다른 PPTX를 낸다. 시험: 작업 11, `apps/web/e2e/scene-worker.spec.ts`.
5. **브라우저의 큰 덱.** 기대: 쪽을 하나씩 읽고, walk하고, 놓아서 메모리가 묶여 있다. 시험: 작업 11, `m0-perf.spec.ts`의 장면 단계. 51쪽 덱에서 워커 최대 메모리 100 MB 이하.
