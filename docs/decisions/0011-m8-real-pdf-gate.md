# 0011. M8 관문: 실제 PDF

- 날짜: 2026-11-19 시작, 2026-11-24 마감. 마지막 측정(r3)은 변환기 커밋 `26f2095`로 2026-11-23 23:47~2026-11-24 02:47(10,759초)에 돌렸고, 결과는 `907b1b6`로 분석 전에 올렸다. 이 뒤의 커밋(이 문서, README)은 변환 출력을 바꾸지 않는다
- 상태: **결정. 작성자의 방향으로 M8을 닫는다.** 남은 실패는 "알려진 한계"로 공개한다. PR은 검토 준비로 돌리고, 병합은 작성자가 정한다
- 범위: M8 작업 계획(계획 10) 전체. 작업 1~2(B단 모으기, 첫 측정), 고침 1~3차례, r1~r3 측정, C단 한 덱
- 읽는 법:
  - "작업 N"은 계획 10의 N번째 작업이다. "M8-Rnn"은 M8을 진행하며 내린 판정이고, 아래 "판정 목록"에 한 줄씩 있다.
  - B단 덱은 매니페스트의 id(`b-` + SHA-256 앞 10자리)로만, C단 덱은 12자리 id로만 적는다. 파일 이름, 제목, 글자는 적지 않는다.
  - "bar"는 출시 기준(§5.5)에 드는 덱이다. 출신이 PowerPoint (Windows)인 덱만 든다. 나머지는 재고 보고만 한다.
  - "통과"는 V1, V2, S1~S7을 모두 넘은 것이다. 글꼴 예외(M8-R3, R9)와 위치 확인 통과(M8-R12)를 포함하고, "게이트 통과"는 위치 확인 통과를 뺀 수다.
  - 원인 이름은 0006~0008의 말을 따랐다. 실제 PDF에서 처음 본 것은 새 이름을 붙였다.

## 결정

1. **M8을 닫는다.** 2026-11-23 작성자가 "판정 정리 + 한 번 더, 그다음 M9"를 정했다. 그 "한 번 더"(3차례)와 r3 측정을 끝냈으므로 M8은 여기서 끝이다. 이어서 하던 고침 차례는 없다.
2. **남은 실패를 "알려진 한계"로 공개한다.** 바 1,781장 가운데 666장이 아직 실패한다(아래 "알려진 한계"). README의 "알려진 한계 / Known limits"가 그 숫자와 쉬운 말의 원인, 약속하지 않는 출신을 적는다.
3. **바 숫자(r3): 통과 1,115장(62.6 %), 실패 666장.** 통과 가운데 39장은 위치 확인 통과(M8-R12)이고, 게이트 통과는 1,076장이다. r2는 1,061 / 720이었다(실패 -7.5 %, 게이트 통과 +15).
4. **멈춤 규칙.** 1차 -30 %, 2차 -10.7 %, 3차 -7.5 %다. "두 차례 연속 10 % 미만"은 이루어지지 않았다(2차가 10 % 위). 그래도 작성자의 방향이 우선한다.
5. **회귀 없음.** atlas, 공개, 비공개 461장은 r2와 쪽마다 같다. 막대 밖 129덱의 구조 회귀망은 나빠진 덱 0, 좋아진 덱 26이다. 변환 충돌 0, PowerPoint 복구 창 0, 검증기 오류 0(r3의 91개 출력).
6. **M9가 작성자에게서 받아야 할 것**은 아래 "M9가 필요로 하는 것"이다.

## 측정 방법

- **M8-R1.** bar 71덱은 다 잰다(V1, V2, S1~S7, PowerPoint 렌더). bar 밖 129덱은 변환, 멈춤, 복구 창, 통째 그림(S1), S1~S6만 재고 렌더하지 않는다(`--off-bar-structural`). 변환기를 바꾼 뒤에는 이 129덱을 `offbar_net`으로 다시 돌려 나빠진 덱이 없는지 본다(M8-R8).
- **r3의 명령.** `python -m harness.fidelity.run --converter deckback --decks public,atlas,private,real,tier-c --bar-only`, 91개 덱×변형, 2,263장(public 82, atlas 350, private 29, tier-c 21, bar 1,781), 10,759초. 단계 실패 0(입력, 변환, 렌더, 정답 렌더), PowerPoint 멈춤 0, 바쁨 0.
- **분류.** `triage fonts`(M8-R3, R9 글꼴 예외를 다시 매김. 최종 숫자는 이것이다)와 `triage causes`(슬라이드마다 원인을 달고 주 원인 하나를 정함)를 썼다. 원본 JSON은 값을 바꾸지 않는다. 분류 표는 r1부터 같은 방법이라 비교할 수 있다.
- **글꼴(M8-R2).** 라운드마다 Office 클라우드 글꼴 폴더를 이름으로 기록한다(`options.cloudFonts`). r3는 32가족으로 r1, r2와 같다. 무료 글꼴 설치 목록(`fonts-tier-b.lock.json`: Nobile, Special Elite, Liberation Sans, OpenSymbol)은 그대로다. 상용 예외는 MS PGothic 하나(9장, `b-8cc9a6b767`)다.

## 차례별로 고친 것

- **작업 1~2 (r0).** B단 200덱을 모으고(위 집계) 하네스를 큰 덱에 맞게 고쳤다(914쪽 덱이 슬라이드마다 PPTX를 다시 열어 2시간 넘게 멈춘 것: `60f2d01`). r0 결과는 1,781장 가운데 통과 618(옛 규칙), 실패 1,163이다. 멈춤 0, 복구 창 0, 검증기 오류 0, 통째 그림 68장(bar 2, bar 밖 66). 가장 큰 원인은 글자 줄 방향 어긋남 369, 기호 글꼴 글머리 175, 쪽 밖 내용 130, 투명 글자 121, 숫자 이름 글꼴 79였다.
- **1차 (r1).** 변환기: 기호 글꼴 글리프를 글꼴 자신의 코드(U+F000 + 코드, `a:sym`)로 쓰고, 쪽 밖 내용을 제자리에 두고, 투명 글자를 알파 0과 prstTxWarp로 써서 PowerPoint가 자기 층을 남기게 하고, 숫자 이름 글꼴의 가족을 프로그램의 다른 이름에서 찾는다. 하네스: bar 요약, bar 밖 n/a, S3 그림-셰이딩 거짓 실패, M8-R3, 클라우드 글꼴 목록, S2 기호 글꼴 정규화, ICC/CMYK 집계, https만 따르는 내려받기. 1차 검토가 위험 1(기호 판정이 cmap만 봄: M8-R8로 막음)과 중요 2(cmap 반복 상한, 이름 길이 상한)를 냈고 고쳤다. 결과 972 / 809(-30 %).
- **2차 (r2).** 변환기: 커닝 판정 K1(격자 잡음 0.10~0.15 pt가 커닝을 켜던 것), K2~K4(짝 간격, 공백 커닝, run 사이 커닝), G1(공백 판정 하나로). F는 채택하지 않았다(M8-R11). 하네스: M8-R9, 분류 O, 막대 밖 회귀망(`offbar_net.py`). 결과 1,061 / 720(-10.7 %).
- **3차 (r3).** 변환기:
  - 한 글자 run의 넓은 간격은 줄이 커닝돼도 그 run의 자간으로 쓴다(`ecc06fd`).
  - 한 줄이 커닝을 보이면 그 상자의 모든 줄을 커닝한다(`4e4e5b2`).
  - 이름표가 부분 집합 태그로 바뀐 글꼴은 서술자의 /FontFamily와 OS/2 스타일을 쓴다(`497081c`). 태그에서 나온 가족이 숫자뿐이면 전처럼 둔다(`424dbc1`).
  - /FontFamily가 없으면 BaseFont의 스타일 꼬리를, OS/2가 없으면 서술자 플래그를 쓴다(`ede956a`).
